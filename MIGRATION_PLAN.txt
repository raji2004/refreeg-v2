SECTION 1 — EXECUTIVE SUMMARY
────────────────────────────────────────────────────────────────────────────────

This document describes the complete strategy and step-by-step execution plan
for migrating the RefreeG v2 platform from:

  CURRENT STACK
  ├── Database  : Supabase (hosted PostgreSQL + Auth + Storage + Edge Functions)
  ├── ORM       : Supabase JS client (@supabase/supabase-js + @supabase/ssr)
  ├── Hosting   : Vercel (Next.js 15 + serverless functions)
  └── Cron/Jobs : Supabase Edge Functions (Deno)

  TARGET STACK
  ├── Database  : PostgreSQL 16 in Docker container (single DB approach)
  ├── ORM       : Prisma 5 (type-safe, schema-first)
  ├── Auth      : NextAuth.js v5 (Credentials + OAuth providers)
  ├── Storage   : AWS S3 (or self-hosted MinIO on VPS)
  ├── Hosting   : AWS EC2 or Hetzner/DigitalOcean VPS (Node.js process manager)
  └── Cron/Jobs : Node-cron inside the Next.js app OR a separate worker process

Estimated total migration duration : 6–8 weeks (with a 2-person team)
Estimated cost difference          : See Section 9
DB decision update                 : Dockerized PostgreSQL only (no RDS/native host DB)

  [ ] 2.3  Create auth.ts (NextAuth config)
        // auth.ts
        import NextAuth from "next-auth"
        import { PrismaAdapter } from "@auth/prisma-adapter"
        import Credentials from "next-auth/providers/credentials"
        import Google from "next-auth/providers/google"
        import { prisma } from "@/lib/prisma"
        import bcrypt from "bcryptjs"

        export const { handlers, auth, signIn, signOut } = NextAuth({
          adapter: PrismaAdapter(prisma),
          session: { strategy: "jwt" },
          providers: [
            Google({
              clientId: process.env.GOOGLE_CLIENT_ID!,
              clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
            }),
            Credentials({
              credentials: {
                email: { label: "Email", type: "email" },
                password: { label: "Password", type: "password" },
              },
              async authorize(credentials) {
                if (!credentials?.email || !credentials?.password) return null
                const user = await prisma.profile.findUnique({
                  where: { email: credentials.email as string },
                })
                if (!user?.password) return null
                const valid = await bcrypt.compare(
                  credentials.password as string,
                  user.password
                )
                if (!valid) return null
                return { id: user.id, email: user.email, name: user.fullName }
              },
            }),
          ],
          callbacks: {
            async jwt({ token, user }) {
              if (user) token.id = user.id
              return token
            },
            async session({ session, token }) {
              if (token) session.user.id = token.id as string
              return session
            },
          },
          pages: {
            signIn: "/auth/signin",
            newUser: "/onboarding",
          },
        })

  BEFORE (Supabase):

      orderBy: { createdAt: "desc" },

SECTION 8 — RISKS & MITIGATIONS
────────────────────────────────────────────────────────────────────────────────

  RISK 1: Password migration (HIGH IMPACT)
    Problem: Supabase passwords cannot be exported.
    Mitigation: Force-reset flow. On first login after migration, any user
    with passwordResetRequired=true is redirected to set a new password.
    A reset email is automatically sent. This affects 100% of existing users.

  RISK 2: Downtime during DNS cutover (MEDIUM IMPACT)
    Problem: DNS propagation can take up to 24 hours.
    Mitigation: Reduce TTL to 60 seconds 24 hours before cutover. Keep
    Supabase + Vercel running as fallback for 48 hours.

  RISK 3: Row Level Security (RLS) gaps (MEDIUM IMPACT)
    Problem: Supabase RLS policies are enforced at the DB level. Prisma
    has no built-in equivalent — security must be enforced at the
    application layer (action/API route level).
    Mitigation: Audit every action file to ensure user ID checks are
    explicit. Create a requireAuth() helper that verifies the session
    user matches the requested resource owner.

  RISK 4: Missing Supabase Realtime features (LOW IMPACT)
    Problem: If any feature uses Supabase Realtime (live subscriptions),
    it will need to be replaced with polling or WebSockets.
    Mitigation: Search for .channel() and .on("postgres_changes") calls.
    None found in current review, but verify before migration.

  RISK 5: Docker PostgreSQL operational reliability (MEDIUM IMPACT)
    Problem: Supabase provides automatic backups, PITR, failover. A Docker-
    hosted PostgreSQL setup requires explicit backup/restore discipline.
    Mitigation: Keep DB in a dedicated container with persistent volume,
    implement daily pg_dump + S3 backup script (Phase 6.4), and document
    monthly restore drills in staging.

  RISK 6: Codebase size (LOW IMPACT)
    Problem: 56 files touch Supabase. Missing one creates a runtime error.
    Mitigation: After Phase 3, run:
    grep -r "supabase\|@supabase" ./src --include="*.ts" --include="*.tsx"
    This should return zero results before going to production.

SECTION 11 — QUICK REFERENCE CHEAT SHEET
────────────────────────────────────────────────────────────────────────────────

  Supabase SDK → Prisma equivalents:

  supabase.from("t").select("*")              → prisma.t.findMany()
  supabase.from("t").select().eq("id", id)    → prisma.t.findUnique({ where: {id} })
  supabase.from("t").insert({...})             → prisma.t.create({ data: {...} })
  supabase.from("t").update({...}).eq("id",id)→ prisma.t.update({ where:{id}, data:{...} })
  supabase.from("t").delete().eq("id", id)    → prisma.t.delete({ where: {id} })
  supabase.from("t").select().in("id", ids)   → prisma.t.findMany({ where:{id:{in:ids}} })
  supabase.from("t").select().gte("c", val)   → prisma.t.findMany({ where:{c:{gte:val}} })
  supabase.rpc("increment", {id, amt})         → prisma.t.update({ data:{field:{increment:amt}} })

  Supabase Auth → NextAuth.js equivalents:

  supabase.auth.getUser()              → auth() then session.user
  supabase.auth.signInWithPassword()   → signIn("credentials", {...})
  supabase.auth.signInWithOAuth()      → signIn("google")
  supabase.auth.signUp()               → prisma.profile.create() + signIn()
  supabase.auth.signOut()              → signOut()
  supabase.auth.updateUser()           → prisma.profile.update()
  supabase.auth.resetPasswordForEmail()→ custom token + Nodemailer email
  const { user } = useAuth()           → const { data: session } = useSession()

  Supabase Storage → AWS S3:

  supabase.storage.from(b).upload(path, file)      → s3.send(new PutObjectCommand({...}))
  supabase.storage.from(b).getPublicUrl(path)      → construct S3 URL directly
  supabase.storage.from(b).remove([path])          → s3.send(new DeleteObjectCommand({...}))
